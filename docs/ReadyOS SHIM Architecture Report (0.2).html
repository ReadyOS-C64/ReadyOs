ReadyOS SHIM Architecture: 0.2.4 Runtime Reality

Implementation-backed report for the active launcher + shim + REU model. This canonical report is intentionally fuller than the short summary docs: it keeps the resident-byte map, the annotated shim routine walkthrough, the profile-driven catalog/release context, and the ABI-vs-implementation nuances that are easy to lose in condensed summaries. This report preserves the previous local snapshot values and adds current 0.2.4 map-backed values after the reserved launcher-overlay REU bank change. Runtime debug suffix letters are intentionally not used as documentation versions.

Current 0.2.5 contract: The full resident shim owns $C600-$C9FF (1024 bytes), with 512 bytes of expansion reserve below the stable ABI at $C800. Physical Skip is the ReadyOS bank; Skip+1 is the first dynamic bank. The app snapshot is $1000-$C5FF ($B600), and schema v5 begins at ReadyOS offset $B600. Historical 0.2.4 discussion below is retained as version history.

What changed from 0.2.3 to 0.2.4:

ReadyOS has a physical REU start bank called Start (READYOS_REU_BANK_SKIP). The fixed ReadyOS region now uses two banks relative to that start point: Start+0 for system/global state and Start+1 for the launcher snapshot/resume bank. Start+2 is the first dynamic allocation bank.

The old fixed app-slot gap has been superseded. App snapshot banks are now assigned by the launcher/cartridge loader and the token-to-physical mapping is published in logical REU bank 0. The resident shim keeps its 512-byte size by fetching one physical-bank byte from that lookup page when switching to a non-launcher app token.

The shim now performs that mapping in $C960-$C99F via reu_setup_logical. The old $C818/log_byte diagnostic path remains only as a legacy entry until its ring storage moves away from active code bytes.

Why the layout matters

  • Everything in $1000-$C5FF is replaceable.
  • The shim survives all loads because it lives above the snapshot window.
  • The hardware stack survives preload and enables the shim’s RTS-based return path.
  • Metadata in $C600-$C9FF stays visible without fetching a management bank from REU.

Annotated Resident Shim Walkthrough

This is a complete commented copy of the current resident shim byte image. The source appendix was refreshed against src/boot/readyos_shim.inc for the 0.2.5 documentation audit. It covers the jump table, every data ABI byte, all live routines, and all padding bytes in the 1024-byte $C600-$C9FF image. The surrounding report remains a preserved 0.2.4 architecture snapshot.

; $C800-$C817: Jump Table (24 bytes, 8 entries)
jt_load_disk    = $C800     ; Load from disk, run
jt_load_reu     = $C803     ; Fetch from REU, run
jt_run_app      = $C806     ; Just run app
jt_preload      = $C809     ; Preload to REU, return
jt_return       = $C80C     ; Return to launcher
jt_switch       = $C80F     ; Switch to another app
jt_reserved     = $C812     ; Reserved compatibility slot (safe no-op)
jt_fetch_bank   = $C815     ; Helper: fetch from bank in A

.byte $4C, $40, $C8         ; $C800: JMP load_disk ($C840)
.byte $4C, $60, $C8         ; $C803: JMP load_reu ($C860)
.byte $4C, $00, $10         ; $C806: JMP $1000 (run app)
.byte $4C, $80, $C8         ; $C809: JMP preload ($C880)
.byte $4C, $00, $C9         ; $C80C: JMP return_to_launcher ($C900)
.byte $4C, $40, $C9         ; $C80F: JMP switch_app ($C940)
.byte $4C, $FF, $C9         ; $C812: reserved helper -> safe RTS
.byte $4C, $F0, $C8         ; $C815: JMP fetch_bank ($C8F0)

.byte $4C, $FF, $C9         ; $C818: deprecated logger -> safe RTS

.byte $00,$00               ; $C81E-$C81F: reserved

; $C821: filename_len

; $C824-$C82F: filename (12 bytes)
; $C830: load_end_lo (KERNAL LOAD end addr low byte, saved by preload)
; $C831: load_end_hi (KERNAL LOAD end addr high byte, saved by preload)
; $C832-$C833: unused
; $C834: current_bank - currently running app
; $C835: last_saved
; $C836-$C838: retired bitmap bytes (reserved; authoritative state is in REU)

Clipboard storage reality

  • Clipboard metadata in RAM: $C702 count, $C710 table.
  • Per-item table layout: each item stores REU bank id, type, and size.
  • Allocator behavior: clip_copy() calls reu_alloc_bank(REU_CLIPBOARD), so payload banks come from the dynamic pool starting at Start+2, with already-used banks skipped by the allocation table.
  • Legacy symbolic contract: some older headers/spec fields still name bank 1 as a clipboard bank, but active payload storage is not single-bank packed there.
Truthful current wording: clipboard metadata is shared in C64 RAM, and clipboard payloads still use one dynamic REU bank per item. The single-bank packed clipboard design has not been implemented yet.

`apps.cfg` and Launcher Lifecycle

Disk-based SKUs

  • Human-edited source: selected cfg/profiles/<profile>.ini catalog
  • Generator/orchestrator: build_support/readyos_profiles.py
  • Disk payload: apps.cfg on drive 8
  • Boot loader: src/boot/boot_asm.s, linked as the normal disk boot path
  • Launcher app: src/apps/launcher/launcher.c, with READYOS_LAUNCHER_VARIANT_EASYFLASH=0
  • Disk-only launcher code includes the file dialog and storage-device helpers, guarded by #if !READYOS_LAUNCHER_VARIANT_EASYFLASH
  • Catalog read mode: apps.cfg,s,r
  • Parsed fields: drive, PRG token, display label, optional hotkey slot, description
  • Assigned at runtime by the launcher: app slot identity and REU preload state

Disk lifecycle

Cold / invalid-resume path
launcher starts → tries launcher-bank resume payload → failure → parse apps.cfg from disk → validate → save fresh LauncherResumeV1
Normal return path
app returns via shim → launcher image restored from the launcher snapshot bank at Start+1 → launcher restarts → restores cached state from launcher bank tail → apps.cfg usually not reread

Cartridge / EasyFlash SKU

  • Human-edited source: cfg/flavors/readyos_easyflash.ini
  • Catalog generator: build_support/readyos_easyflash.py catalog-header
  • Generated launcher catalog: src/generated/launcher_easyflash_catalog.h
  • Generated boot/shim REU config: src/generated/readyos_easyflash_reu_config.inc
  • Generated cartridge layout: src/generated/easyflash_layout.inc and obj/easyflash_layout.json
  • Custom booter: src/boot/boot_easyflash_asm.s plus src/boot/easyflash_shim.s
  • Launcher app: src/apps/launcher/launcher_easyflash.c, which defines READYOS_LAUNCHER_VARIANT_EASYFLASH=1 and includes launcher.c
  • ReadyShell cartridge build: bin/readyshell_easyflash.prg with RS_C64_OVERLAY_PRELOADED=1

Cartridge lifecycle

Before launcher menu
the EasyFlash booter copies the shim, restores the EasyFlash launcher payload into the launcher snapshot bank, and preloads the cartridge catalog apps plus the ReadyShell overlay cache into REU.
Launcher catalog path
the EasyFlash launcher does not open apps.cfg. It consumes generated arrays such as READYOS_EASYFLASH_APP_COUNT, readyos_easyflash_prgs, readyos_easyflash_labels, readyos_easyflash_descs, readyos_easyflash_default_slots, and readyos_easyflash_app_banks.
Disk boot never parses apps.cfg; the disk launcher does. Cartridge boot never depends on apps.cfg at runtime; its app catalog, physical preload plan, and ReadyShell overlay preload plan are generated into the EasyFlash build.
Current release matrix: there are seven active profiles. precog-dual-d71 is the default full-content verification target and the only one that uses PREBOOT -> SETD71 -> BOOT. The other six current profiles use direct PREBOOT -> BOOT.

Current memory contract

  • Real app snapshot window: normal ReadyOS apps link and resume inside $1000-$C5FF, not $1000-$BFFF.
  • Why this is trustworthy: cfg/ready_app.cfg defines MAIN as $1000 + $B600, and the shim copies exactly $B600 bytes during REU stash/fetch.
  • Suspend/resume split: REU bank offsets $0000-$B5FF hold the raw app snapshot, and offsets $B600-$FFFF hold the per-app resume payload.
  • Report consequence: app headroom must be measured to $C5FF, while logical resume state belongs to the REU tail outside that snapshot.
  • Code/docs alignment: the boot-loader memory-map comment, linker configs, shim implementation, and verifiers all use the same $1000-$C5FF app snapshot window.

Interpreting slack

  • Normal apps: cfg/ready_app.cfg puts BSS directly inside the $1000-$C5FF app window.
  • Aligned writable slack is not always heap: the table reports what is left after BSS and even alignment, but that should not be read as a proven malloc heap unless the app actually initializes and uses it that way.
  • Simple Files / Simple Cells: those apps use dedicated linker configs with an explicit __STACKSIZE__ = $0070 reserve below $C600, so their slack figures include a deliberate stack guardrail and are not unconstrained heap.
  • Overlay app: readyshell uses cfg/ready_app_overlay.cfg, not the normal app linker contract.
  • Historical resident ReadyShell image: the previous local snapshot ended at $9B74, with a much smaller resident image. Those values are retained only for historical comparison.
  • Current resident ReadyShell image: the current 0.2.4 map has RODATA 1037, DATA 71, resident BSS $8340-$8536 (503 bytes), resident heap $8538-$8DFD (2246 bytes), and overlay load-address bytes at $8DFE-$8DFF. The prompt editor now lives in overlay 9, rsedit.prg, cached in REU bank $42.
  • True current ReadyShell limit: overlay payload fit is tighter than the resident heap gap. Current overlay1 is $8E00-$C0CC and leaves 1331 bytes; overlay2 leaves 303 bytes; overlay3 leaves 3064 bytes; overlay4 leaves 2452 bytes; overlay5 leaves 4131 bytes; overlay6 leaves 3 bytes; overlay7 leaves 6258 bytes; overlay8 leaves 7737 bytes; overlay9 leaves 12334 bytes.
  • Overlay guardrail: release overlay size is $3800 and debug overlay size is $3B00. The old explicit-C-stack-reserve wording is retained as historical shorthand, but current safety depends on ONCE/BSS ending below __OVERLAY_LOADADDR__, overlays loading at $8E00, and ReadyShell stack relocation being handled separately.

Transition Flows

Preload sandwich

1. Launcher writes target bank, filename, and drive into shim bytes.
2. Launcher calls JSR $C809.
3. Shim stashes launcher image to the launcher bank at Start+1.
4. Shim KERNAL-loads target app into $1000.
5. Shim saves real load end to $C830-$C831.
6. Shim stashes loaded app to target logical bank, sets bitmap, restores launcher, and RTSes.

Return to launcher

1. App jumps to $C80C through TUI helper.
2. Shim stashes current app to its bank.
3. Shim updates bitmap and records last_saved.
4. Shim fetches the launcher bank at Start+1.
5. Shim sets current_bank = 0 and jumps to $1000.
6. Launcher restarts and usually restores cached menu/catalog state from the launcher bank tail.

Launch from REU

1. Launcher saves LauncherResumeV1.
2. Launcher stashes itself to the launcher bank at Start+1.
3. Launcher writes target scratch bytes and sets current_bank.
4. Launcher jumps to $C803.

Launch from disk

1. Launcher saves LauncherResumeV1.
2. Launcher stashes itself to the launcher bank at Start+1.
3. Launcher writes filename and patched drive bytes.
4. Launcher sets current_bank.
5. Launcher jumps to $C800.

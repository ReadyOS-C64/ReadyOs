What the Chart Says

The launcher is not tight because of one large static buffer. It is tight because code that is only needed during browsing now lives permanently in the app image. ReadyShell is tight in a different way: its resident core is controlled, and the prompt editor has moved to overlay 9, but every overlay must still fit the fixed $3800 execution window.

Launcher BSS is mostly catalog state: about 2.0 KB for live app labels/descriptions/files and about 2.1 KB for the duplicate catalog cache saved into the resume tail. The manifest browser adds about 370 bytes of static dialog state; PRG bytes are loaded by the shim path rather than copied through a large launcher RAM buffer.

The most valuable memory strategy is therefore not moving the global app ceiling. It is moving infrequent workflows out of the resident image. ReadyShell just demonstrated that again: extracting the prompt editor recovered about 1.1 KB of resident heap.

Design Direction

ReadyOS already has a sound foundation: a stable snapshot window, resident shim, REU-backed app banks, and opt-in resume tails. The next memory win should preserve that stability and add a first-class way to make rare workflows transient.

In practice: leave the ABI alone, make launcher browse/load nonresident, and use ReadyShell-style overlays only where a feature has enough weight to repay the complexity.
